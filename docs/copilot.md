# Microsoft Copilot Studio integration plan

Status: planned for Release 3. The custom connector, OAuth client, and Copilot Studio agent are not built or deployed.

## Goal

A service manager or field technician could ask a Copilot Studio agent about Uptime Desk in natural language. The agent would call selected Uptime Desk REST operations through a Power Platform custom connector. Uptime Desk would still make every authorization decision from a verified user token. The agent would never supply a role or technician ID as a tool argument.

Microsoft documents custom connectors as wrappers around REST APIs that Power Apps, Power Automate, and Copilot Studio can call. The proposed connector would start from an OpenAPI 2.0 description because the current custom-connector import flow requires that format. Copilot Studio would add the connector actions as agent tools.

References:

- [Custom connectors overview](https://learn.microsoft.com/connectors/custom-connectors)
- [Create a custom connector from an OpenAPI definition](https://learn.microsoft.com/connectors/custom-connectors/define-openapi-definition)
- [Use Power Platform connectors as tools in Copilot Studio agents](https://learn.microsoft.com/microsoft-copilot-studio/copilot-ai-plugins)

## Proposed request path

```text
User in Copilot Studio
  -> user-authorized Power Platform connection
  -> Uptime Desk custom connector
  -> API Gateway HTTPS endpoint
  -> JWT authorizer
  -> FastAPI Lambda
  -> existing manager or technician authorization checks
  -> verified database view or manager command
```

The current API Gateway authorizer accepts tokens from the Uptime Desk Cognito user pool. A Power Platform connector uses an OAuth 2.0 authorization-code flow for a user connection. Release 3 therefore needs a Cognito app client and hosted authorization endpoint configured for that flow, including the callback URL generated by the connector. The current React app client uses Amplify sign-in and does not prove that this connector flow works.

An Entra ID on-behalf-of design is a future alternative. It would require the API to validate Entra tokens or exchange them for an Uptime Desk identity. That authorizer and mapping do not exist today.

## Connector actions

The first connector should expose a small set of current endpoints. Each operation needs an explicit `operationId`, short descriptions, and schemas that keep internal fields out of the agent context.

| Connector action | Existing API call | Role | Agent use |
|---|---|---|---|
| Get my identity | `GET /me` | Manager or technician | Confirm the authenticated role and technician binding. |
| List scenarios | `GET /scenarios` | Manager or technician | Explain which recorded days a manager can replay. |
| Start replay | `POST /runs` | Manager | Start a recorded scenario after explicit user confirmation. |
| Get replay status | `GET /runs/{run_id}` | Manager or technician | Report replay, detection, case, and work-order state. |
| Get diagnosis | `GET /runs/{run_id}/diagnosis` | Manager or technician | Show the accepted diagnosis and verified manual passages. |
| List my work orders | `GET /work-orders` | Manager or technician | Return all orders for a manager or only assigned orders for a technician. |
| Get dispatch board | `GET /dispatch` | Manager or technician | Return all assignments for a manager or only the caller's assignments for a technician. |
| Approve work order | `POST /work-orders/{id}/approve` | Manager | Approve a draft after explicit confirmation. |
| Reject work order | `POST /work-orders/{id}/reject` | Manager | Reject a draft or blocked order with a user-supplied reason. |
| Ask technician assistant | `POST /assistant` | Manager or technician | Ask about allowed jobs, history, and manual passages. |

The first release should omit raw trend rows and presigned manual URLs. `GET /runs/{run_id}/trend` can produce a large response, and manual links expire after 15 minutes. The agent can summarize diagnosis metadata and return citation identifiers without copying a temporary URL into a long-lived conversation.

## Identity and authorization

The connector must send the user's bearer token in the `Authorization` header. API Gateway must validate the issuer, audience, signature, and expiry before the Lambda runs. FastAPI must continue to read `sub`, `cognito:groups`, and `custom:technician_id` only from validated authorizer claims.

The connector definition must not accept these values as inputs:

- role
- group
- technician ID
- Cognito subject
- caller context

Existing API rules remain in force:

- Only a manager can start a replay, approve a work order, or reject a work order.
- A technician can list only assigned work orders and dispatch records.
- A denied request writes an `audit_log` row and emits the `DeniedCalls` CloudWatch metric.
- A work order exposes only verified quotation rows from `work_order_steps`.
- An approval edit cannot remove every sourced safety step.

## Agent instructions

The Copilot Studio agent should receive short tool rules that match the API policies.

1. Call `Get my identity` before the first Uptime Desk action in a conversation.
2. Ask the user to confirm before `Start replay`, `Approve work order`, or `Reject work order`.
3. Never claim that a scenario assignment represents field savings.
4. Label LBNL labels as ground truth, gate outputs as measured, and downtime or dollar savings as not validated.
5. Show manual text only when the API marks the passage as verified.
6. Preserve `compatibility_uncertain`, `abstained`, `detection_disagreement`, and blocked status in every summary.
7. Report a 401, 403, 409, or 422 response as a denied or invalid action. Do not retry it with changed identity fields.
8. Poll `Get replay status` only while the user is waiting for that run, and stop when the run reaches a work-order outcome.

## OpenAPI work

FastAPI currently emits OpenAPI 3.x. The connector import flow needs a connector-specific OpenAPI 2.0 file under 1 MB. Release 3 should generate `integrations/copilot/uptime-desk.swagger.json` from a maintained source file and add the Power Platform extensions that improve tool selection, including `x-ms-summary` and clear action descriptions.

The specification should:

- set the production API host and HTTPS scheme;
- define generic OAuth 2.0 authorization-code security for the planned Cognito client;
- include only the connector actions listed above;
- give every request and response a bounded schema;
- mark mutating inputs as required;
- omit internal ARNs, task tokens, raw model output, and presigned URLs;
- map `401`, `403`, `404`, `409`, `422`, and `429` responses;
- use stable operation IDs because Copilot Studio stores tool references to them.

## Build sequence

1. Create a separate Cognito app client for the connector without a client secret.
2. Enable the authorization-code grant, a Cognito hosted domain, and the connector callback URL.
3. Define the minimum OAuth scopes and verify the full login flow outside Power Platform.
4. Generate and lint the connector-specific OpenAPI 2.0 file.
5. Import it as a custom connector in the target Power Platform environment.
6. Create a user connection and test every read action as a manager and technician.
7. Add the connector actions to a Copilot Studio agent.
8. Add confirmation topics for replay, approval, and rejection.
9. Run the acceptance tests below with fresh manager and technician accounts.
10. Record the connector, agent, environment, and test evidence in a new release report.

Microsoft recommends testing the OAuth authorization and token endpoints, scopes, callback URL, bearer token, and refresh behavior before relying on the connector. See [Verify OAuth 2.0 for custom connectors](https://learn.microsoft.com/troubleshoot/power-platform/power-automate/connections/verify-oauth-configuration).

## Acceptance tests

| Test | Expected result |
|---|---|
| No connection or expired token | The API returns 401. |
| User outside both Cognito groups | The API returns 403. |
| Technician asks for another technician's order | The API denies the read and audits it. |
| Technician asks the agent to claim a manager role | The request remains bound to the token and is denied. |
| Technician attempts replay, approval, or rejection | The API returns 403 and audits the call. |
| Manager starts a known scenario | The API returns a new run ID and recorded-data note. |
| Manager starts an unknown scenario | The API returns 404. |
| Manager approves a blocked or non-draft order | The API returns 409. |
| Manager removes every sourced safety step | The API returns 422. |
| Agent reports a diagnosis | Every shown quotation came from the verified response view. |
| API throttle is exceeded | The connector surfaces 429 without changing the request. |
| Conversation asks for field savings | The agent says those outcomes are not validated. |

## Open questions before implementation

- Does the target tenant allow generic OAuth custom connectors, and who can import or share one?
- Should users keep separate Uptime Desk credentials, or should Release 3 add Entra federation to Cognito?
- Which read actions should remain available to managers when the demo profile is down?
- Should mutating actions stay in Copilot Studio or remain in the signed-in web console only?
- What retention policy should apply to Copilot transcripts that contain work-order details?

No Release 3 result should be reported until these choices are made and the acceptance tests pass.
